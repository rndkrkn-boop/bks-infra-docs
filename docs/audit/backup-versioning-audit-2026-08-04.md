# Аудит стратегии бэкапов и переход на версионирование

**Дата:** 2026-08-04
**Область:** `host-infra/backup/`, `/home/admin/backups/bks/`, `bks-backup.timer`
**Карточка:** kanban architecture-improvements #8 «Database backup versioning»
**Исполнитель:** bks/infra

## 1. Что было (v1)

Ежедневный `bks-backup.sh` (agents-v2 Phase 0.10) снимал 8 артефактов в плоский
каталог `/home/admin/backups/bks/` с датой в имени файла
(`kanban-production-20260803.db`), ротация — `find -mtime +7`, retention 7 дней,
restore-тест — ручной «ежеквартально» по README.

Таймер работал: последний запуск 2026-08-04 03:04, до него ежедневно.

## 2. Найденные дефекты

Все три подтверждены наблюдением, а не выведены из чтения кода.

### D1. Тихая деградация: «успешный» бэкап без данных (severity: high)

С `2026-08-03T17:17` и далее все пять kanban DB логировались как
`SKIP: default DB not found (board not yet created or empty)` — sandbox был
пересоздан, путь `/sandbox/.hermes/kanban.db` внутри не найден. `SKIP` не
инкрементировал `ERRORS`, поэтому:

* набор за 2026-08-04 не содержит ни одной kanban DB (`ls` подтверждает:
  свежайшие — `*-20260803.db`);
* `.last_backup` за 2026-08-04 записан;
* watchdog `backup_freshness` оставался зелёным (он смотрит возраст новейшего
  файла, а свежие `qdrant-20260804.tar.gz` существовали).

Это рецидив инцидента 2026-07-21, ради которого написано правило BCP-001:
проверка свежести не равна проверке полноты.

### D2. Дата в имени файла ⇒ перезапись версий (severity: high)

Три прогона 2026-08-04 (`17:17`, `17:28`, `19:04` UTC) последовательно
перезаписали `memgraphrag-data-20260804.tar.gz` и `qdrant-20260804.tar.gz`.
Версий не существует: плохой прогон затирает хороший, и вернуться к первой
(корректной) копии дня нечем.

### D3. Ротация по `mtime`, а не по возрасту данных (severity: medium)

`find -mtime +7` смотрит время модификации inode. Перезапись из D2 «омолаживает»
файл, поэтому артефакты одного логического набора истекают в разные моменты, а
возраст данных ротацией вообще не учитывается. Наблюдаемое следствие: 2026-08-03
удалились ровно `*-20260727.db`, тогда как `memgraphrag-data-20260727.tar.gz`
остался — набор распался на части с разным сроком жизни.

### D4. Нет контрольных сумм и проверки целостности (severity: medium)

Артефакт считался годным по наличию и ненулевому размеру. Битая страница sqlite
или усечённый gzip прошли бы незамеченными до момента реального восстановления.

### D5. Нет автоматической проверки восстановления (severity: medium)

README предлагал ручной ежеквартальный restore-тест. Последний
задокументированный — 2026-07-09, и он подтверждает набор, которого в хранилище
уже нет. Проверка, зависящая от того, что человек про неё вспомнит, в отчёте
выглядит как проверка, но ею не является.

### D6. Нулевой артефакт выглядел существующим (severity: low)

При неудачном `tar` профилей `cat` всё равно создавал пустой
`profiles-YYYYMMDD.tar.gz`. Файл существовал, и любая проверка «по наличию»
считала его бэкапом.

## 3. Что сделано

| Дефект | Исправление |
|---|---|
| D1 | Полноту объявляет `backup-manager.py` по `manifest.json`, а не скрипт. Отсутствие обязательного источника — `ERROR`, а не `SKIP`; сервис выходит с кодом 1 |
| D2 | Единица хранения — иммутабельный `snapshots/<YYYYMMDDTHHMMSSZ>/`; два прогона в сутки дают два снапшота |
| D3 | GFS-ретеншен по `snapshot_id` (7 дневных / 4 недельных / 6 месячных / 2 годовых, `min_keep = 3`); слот занимает только `status: complete` |
| D4 | sha256 каждого артефакта в манифесте; `verify` делает `PRAGMA integrity_check` и полный обход tar |
| D5 | `restore-drill` + `bks-backup-drill.timer` (понедельник 04:30), отчёты в `drills/`, отказ восстанавливать в production-пути |
| D6 | Пустой файл удаляется на месте — манифест видит артефакт отсутствующим, а не «подозрительно маленьким» |

Дополнительно: watchdog получил отдельную проверку `backup_recoverability`
(полнота новейшего снапшота + давность drill). Семантика существующей метрики
`backup_freshness` намеренно не менялась.

## 4. Проверки

Синтетические (`tests/test_backup_manager.py`, 34 теста, все PASS): полнота и
статусы манифеста, GFS-слоты и границы ISO-недели, `min_keep`, grace-окно для
неполных снапшотов, идемпотентность `apply`, детект подмены байта / битой
страницы sqlite / усечённого tar, неизменность архива при verify, отказ
восстанавливать в `/etc` и в корень хранилища, path traversal при распаковке,
миграция v1 по дате из имени.

На реальных данных (копия набора 2026-08-03 в `/tmp`, прод-хранилище не
изменялось):

* `migrate --apply` → `20260803T000000Z`, `status: complete`, 8/8;
* `verify --all` → OK;
* `restore-drill` → OK, 8/8 артефактов восстановлены:
  `integrity_check: ok` на всех пяти БД, 14 задач и 74 события в
  production-доске, 2534 файла в профилях, 1925 файлов в Qdrant.

Также воспроизведён ключевой шаг съёма kanban (`VACUUM INTO` сквозь два уровня
`bash -c`, как это делает `nemohermes sandbox exec`): 42/42 строки,
`integrity_check: ok`.

## 5. Остаточные риски

| Риск | Статус |
|---|---|
| `qdrant.tar.gz` снимается live-tar без Qdrant snapshot API: распаковываемость доказана, консистентность коллекций — нет | Открыт, целевой фикс — snapshot API либо backup при остановленном контейнере |
| Бэкап хранится только на том же хосте: единственная точка отказа по диску/железу | Открыт, off-site реплика не входит в область карточки #8 |
| Причина D1 (kanban DB не находятся внутри пересозданного sandbox) — не дефект бэкапа | Открыт, относится к rebuild-багу sandbox; после исправления снапшоты станут `complete` автоматически |

Первые полные снапшоты v2 появятся после деплоя (`DEPLOY.md`, раздел
«Backup: контракт полноты») и первого прогона таймера; до устранения причины D1
`status` будет честно репортить `partial` вместо ложного успеха v1.
