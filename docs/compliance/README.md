# Автоматизация комплаенс-аудита

Комплаенс здесь — не декларация в вики, а исполняемый набор правил, который
падает в CI. Документ описывает контракт: где правила, как они проверяются,
куда уезжают отчёты и что делать, когда правило провалилось.

## Состав

| Артефакт | Что это |
|----------|---------|
| `compliance/rules.toml` | каталог правил и реестр исключений — источник истины |
| `scripts/compliance-audit.py` | движок: прогон правил, JSON/Markdown/Prometheus |
| `scripts/compliance-dashboard.py` | самодостаточный HTML-дашборд из JSON-отчёта |
| `compliance/grafana-dashboard.json` | тот же комплаенс в Grafana, но во времени |
| `ci/compliance-report.sh` | один вход для CI и host-таймера |
| `tests/test_compliance_audit.py` | тесты движка (17 штук) |
| `docs/compliance/reports/` | датированные отчёты, приложенные к аудиту |

## Принципы, на которых это построено

1. **Правило — данные, не код.** Требование заводится правкой TOML; Python
   трогают только при появлении нового *типа* проверки. Каталог правил можно
   ревьюить отдельно от движка.
2. **Только детерминированные проверки.** Ни одна проверка не спрашивает LLM
   и не ходит в сеть. Комплаенс, чей вердикт зависит от температуры модели,
   доказательством не является — тот же принцип, что у
   `kanban-integrity-sweep.py` в bksamotsvety.
3. **Zero-dep.** Только stdlib: CI-джобы стартуют на `python:3.11-slim` без
   `pip install`, а непиннутая зависимость в CI в этом проекте уже роняла
   пайплайн (`ruff` 0.16.0, коммит c0eece8).
4. **Область — `git ls-files`.** Проверяется то, что под контролем версий, а
   не рабочее дерево: иначе «у меня локально зелено» перестаёт что-то значить.
5. **Находки маскируются.** Секрет-правила печатают место находки и длину, но
   не значение: отчёт с секретом внутри — это ещё одна копия секрета, теперь
   ещё и в артефактах пайплайна.

## Как запустить

```bash
# быстрый прогон с выводом в консоль
python3 scripts/compliance-audit.py

# полный набор артефактов (JSON + Markdown + HTML + метрики)
COMPLIANCE_OUT_DIR=/tmp/compliance bash ci/compliance-report.sh

# тесты движка
python3 -m pytest tests/test_compliance_audit.py -q
```

Коды возврата `compliance-audit.py`: `0` — нарушений уровня гейта нет,
`1` — есть блокирующее нарушение, `2` — сломан сам инструмент (битый TOML,
не git-репозиторий). Разделение важное: «инструмент не смог» и «требование
нарушено» — разные события, и `2` нельзя обрабатывать как «всё хорошо».

## Гейт и severity

`[gate].block_at` в `rules.toml` задаёт порог блокировки; сейчас `high`.
Правила `medium`/`low` попадают в отчёт и в метрики, но пайплайн не роняют:
гейт, который блокирует всё подряд, в первый же аврал отключают целиком —
и тогда не работает вообще ничего.

Балл считается взвешенно (critical 10, high 5, medium 2, low 1). Правило со
статусом WAIVED **не** засчитывается как выполненное: принятый риск остаётся
риском, иначе достаточно выписать себе исключений до 100%.

## Исключения (waivers)

Waiver — это осознанно принятый риск с владельцем, тикетом и сроком:

```toml
[[waivers]]
rule = "SUP-001"
reason = "..."
owner = "bks/infra"
ticket = "kanban architecture-improvements #7"
expires = "2026-10-01"
```

Просроченный waiver не применяется: правило снова блокирует пайплайн, а факт
просрочки уходит в отчёт отдельной находкой и в метрику
`bks_compliance_waiver_expires_timestamp_seconds`. Панель Grafana «Ближайший
waiver истекает через» существует ровно для того, чтобы срок пересматривали
заранее, а не в день, когда пайплайн внезапно покраснел.

## Как добавить правило

1. Дописать блок `[[rules]]` в `compliance/rules.toml`, обязательно с
   `reference` на конкретную статью/пункт/NFR. Правило без основания — это
   чьё-то мнение, его нельзя ни оспорить, ни отменить осознанно.
2. Выбрать тип проверки из готовых: `forbidden_pattern`, `required_pattern`,
   `paths_tracked`, `paths_not_tracked`, `paths_ignored`, `max_age_days`.
3. Прогнать `python3 scripts/compliance-audit.py` и убедиться, что правило
   **умеет падать**: временно сломайте проверяемое условие. Правило, которое
   нельзя провалить, комплаенс не измеряет — оно его имитирует.
4. Если нужен новый *тип* проверки — добавить функцию в `CHECKS`
   (`scripts/compliance-audit.py`) и тест в `tests/test_compliance_audit.py`.

Валидация каталога строгая: опечатка в `severity`, неизвестный тип проверки
или waiver на несуществующее правило дают код возврата 2, а не молча
пропущенное требование.

## Автоматическая отчётность

### GitLab CI

Джоб `compliance-audit` (stage `compliance`) запускается на MR, на дефолтной
ветке, по расписанию и при изменении файлов комплаенса. Публикует
`.compliance-out/` как artifacts на 90 дней: `report.json`, `report.md`,
`dashboard.html`. Джоб `compliance-tests` гоняет тесты движка.

`GIT_DEPTH: "0"` в джобе обязателен: правило BCP-002 смотрит дату последнего
коммита документов аудита, а при shallow clone этой даты у файла может не
быть — проверка провалилась бы на пустом месте.

Регулярный прогон настраивается в GitLab UI: **CI/CD → Schedules**, ежедневно.
Прогон по расписанию ловит дрейф — например, waiver, который истёк вчера, —
а не только правки, которые кто-то догадался связать с комплаенсом.

### Host-таймер и Prometheus

На хосте тот же скрипт пишет метрики в textfile-каталог node_exporter
(атомарно, через временный файл и `mv` — collector читает каталог по своему
таймеру и покажет полуфайл как битую экспозицию):

```ini
# /etc/systemd/system/bks-compliance.service
[Unit]
Description=BKS compliance audit
After=network-online.target

[Service]
Type=oneshot
User=admin
WorkingDirectory=/home/admin/projects/nemohermes_bks
Environment=COMPLIANCE_METRICS_DIR=/var/lib/node_exporter/textfile
Environment=COMPLIANCE_GATE=off
ExecStart=/usr/bin/env bash ci/compliance-report.sh
```

```ini
# /etc/systemd/system/bks-compliance.timer
[Unit]
Description=Daily BKS compliance audit

[Timer]
OnCalendar=*-*-* 04:30:00
Persistent=true

[Install]
WantedBy=timers.target
```

`COMPLIANCE_GATE=off` здесь намеренно: на хосте задача — снять метрику, а не
уронить unit. Блокирует пусть CI, где есть кому чинить.

Юниты живут в отдельном репозитории host-infra рядом с
`bks-watchdog`/`bks-backup` — здесь они приведены как контракт, а не как
задеплоенная конфигурация.

## Дашборды

Два представления, у каждого своя работа:

- **HTML** (`dashboard.html`) отвечает на вопрос «что нарушено прямо сейчас»:
  балл, плитки статусов, разрезы по критичности и по требованиям регуляторов,
  реестр исключений, полная таблица правил с находками. Самодостаточный файл
  без CDN и внешних шрифтов — открывается из артефактов пайплайна и на хосте,
  у которого исходящий TLS исторически нестабилен.
- **Grafana** (`compliance/grafana-dashboard.json`) отвечает на вопрос «как
  это менялось и не пора ли алертить»: история балла, число блокирующих
  нарушений, возраст последнего прогона, ближайший истекающий waiver.

Импорт: Grafana → Dashboards → Import → загрузить JSON → выбрать Prometheus.
Провижининг живёт в отдельном репозитории monitoring; известная гоча — правки
provisioning не применяются без пересоздания контейнера Grafana, файл после
деплоя нужно проверить внутри контейнера.

Метрики, на которые стоит завести алерты:

| Выражение | Смысл |
|-----------|-------|
| `bks_compliance_blocking_rules > 0` | появилось блокирующее нарушение |
| `time() - bks_compliance_last_run_timestamp_seconds > 172800` | аудит перестал запускаться |
| `bks_compliance_waiver_expires_timestamp_seconds - time() < 1209600` | waiver истекает через две недели |

Алерт на возраст прогона — самый важный из трёх. Автоматизированный комплаенс
обычно отказывает не громко (правило упало), а тихо: задача перестала
запускаться, а дашборд продолжает показывать последний зелёный результат.

## Текущее покрытие (v1.0.0)

14 правил. Каждое ссылается на реальный артефакт репозитория и умеет падать.

| ID | Требование | Основание | Severity |
|----|-----------|-----------|----------|
| SEC-001 | секретный материал не в git | NFR-5; 152-ФЗ ст.19 | critical |
| SEC-002 | runtime-репо с секретами изолированы | NFR-5 | critical |
| SEC-003 | `.env`/ключи не отслеживаются | NFR-5; GDPR art.32 | critical |
| PII-001 | chat_id и персональные данные не публикуются | 152-ФЗ ст.5 ч.4 | high |
| PII-002 | PII-контур описан (`org-pii` + pii-cleaner) | NFR-6; GDPR art.25 | high |
| AC-001 | доступ к графу разграничен per-namespace | NFR-6; ISO 27001 A.5.15 | high |
| SUP-001 | нет плавающих тегов образов в CI | SLSA Build L2 | high |
| SUP-002 | зависимости CI запиннены | SLSA Build L2 | high |
| SUP-003 | обвязка подписи образов в репозитории | SLSA Provenance | medium |
| BCP-001 | контракт полноты бэкапа численный | NFR-4; ISO 27001 A.8.13 | high |
| BCP-002 | аудиторские свидетельства свежее 90 дней | ISO 27001 A.5.35 | medium |
| LOG-001 | срок хранения журналов задан явно | GDPR art.5(1)(e) | medium |
| GOV-001 | лицензия на месте | внутренний регламент | low |
| GOV-002 | прод-конфигурация агентов только через git | NFR-9; ISO 27001 A.8.32 | medium |

Чего эти правила **не** проверяют (честные границы):

- **Рантайм.** Права `0600` на файлы секретов, видимость процессов, реальный
  состав бэкапа на диске, живой ACL MemGraphRAG — всё это проверяется на
  хосте (watchdog, аудиты), а не по содержимому репозитория. Здесь проверяется
  наличие и непротиворечивость контракта, а не его исполнение.
- **История git.** Сканируется текущее состояние файлов, не прошлые коммиты.
  Утёкший и позже удалённый секрет правилом SEC-001 не ловится — его нужно
  перевыпускать, а не убирать из HEAD.
- **Смысл документов.** `required_pattern` проверяет наличие маркера, а не
  то, что раздел описывает правду. Это анти-drift-проверка того же класса,
  что `check-docs-consistency.py`, а не замена аудиту.

Первый прогон (2026-08-04) нашёл реальное нарушение PII-001: chat_id
ops-группы в трёх местах в отслеживаемых документах, при действующем правиле
проекта «не выносить chat_id в логи и отчёты». Значение отредактировано до
`<ops-group-chat-id>`, правка помечена в самом документе.
